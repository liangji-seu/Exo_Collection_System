## 一、要解决的问题

后续要用 XINGYING 录制的 `.cap`（动捕 Marker + 六维力测力台）做 **OpenSim 逆动力学反解力矩**，
希望得到的力矩能**与我们的其他模态（超声 / IMU / 编码器 / 肌电）在时间上同步**。

需要确认并解决：`.cap` 时间轴 ↔ 主机时钟时间轴之间，目前只有「起始锚点」级的粗同步，精度不足。

## 二、现状（同步架构审查结论）

### 1. 软件采集的 4 个模态之间：已同步 ✅

所有软件模态共用**主机单调时钟** `perf_counter_ns()`（`host_monotonic_ns`）作为对齐权威，
每个采样都写 `host_monotonic_ns` + `device_time` + `sample_index` 到 HDF5。
见 `src/exo_collection/timing/clock.py`、`src/exo_collection/writers/hdf5_signal.py`。

### 2. XINGYING 的 .cap（动捕 + 测力台）：只有「起始锚点」粗同步 ⚠️

采集端通过 UDP 向 XINGYING 发 `CaptureStart` / `CaptureStop`（7060 端口），
并监听 7061「捕获--触发」广播，在**收到广播那一刻**打 `host_monotonic_ns`，写入
`raw/xingying_trigger.jsonl`。最终在 manifest 里登记一条 **`offset_only=True`** 的对齐记录：
「.cap 第 0 帧 ↔ 收到 CaptureStart 广播时刻的主机单调时间戳」。

**四个缺口：**
1. **起始锚点有未知延迟** —— 时间戳打在「收到广播」时，不是 XINGYING 真正开始录第 0 帧时（UDP 往返 + XINGYING 内部处理 + 监听线程唤醒，几毫秒~几十毫秒不确定）。
2. **没有漂移校正** —— `offset_only` 只拟合偏移，不拟合斜率；XINGYING 晶振 vs 主机时钟随 trial 时长累积漂移。
3. **停止锚点不可靠** —— XINGYING 停止时可能不广播 `CaptureStop`，代码里是手动「补记」近似值，实际常只有一个可靠锚点（起始）。
4. **没有消费端** —— src 里没有任何 `.cap/.trb/.anb` 读取与时间映射代码，对齐只被写成元数据，尚无代码把 cap 帧时间真正换算到主机时间轴。

> 注意：**动捕和测力台两者之间是同步的**（都录在同一个 .cap、同一帧时钟）。
> 纯逆动力学（运动学 + 地面反力）内部没问题；问题只在「cap 时间轴 ↔ 我们模态时间轴」这一层。

## 三、XINGYING 远程控制 API 中的同步相关能力

来源：`远程控制API使用说明.docx`。以下是与同步直接相关的内容。

### 1. `SetSyncDevice` —— 同步盒（治本方案，硬件）

配置 Nokov 同步盒（命令需填 `DeviceID` = 同步盒序列号）：

- **InputSource（输入，让 XINGYING 帧时钟锁定外部信号）**
  - `0x0001` 内部时钟
  - `0x0004` Genlock VS 信号
  - `0x0040` Isolated In 信号
  - `0x0080` TTL In 1 信号
  - `0x0100` TTL In 2 信号
  - `0x0200` SMPTE 时间码同步
- **InputMode**
  - `0x0001` 同步输入模式 1：产生一个同步触发脉冲，上升沿触发，同步盒开始连续工作
  - `0x0002` 同步输入模式 2：多脉冲连续触发，触发一次同步一帧
- **TTLOut 1-4**
  - `0` 不使能
  - `0x0001` 模式 1：连续输出多个脉冲，频率=帧率×倍率，空闲高电平（= 每帧一个脉冲）
  - `0x0002` 模式 2：输出一定脉宽的脉冲
  - `0x0003` 模式 3：连续输出脉冲，频率=帧率×倍率，空闲低电平
- **SmpteOut**：`0` 不用 / `0x0001` 使用 SMPTE 时间码输出
- **NetOut**：`0` 不用 / `0x0001` 使用 NET 同步输出

**含义**：可用同步盒的 **TTL Out（每帧一个脉冲）** 接进我们系统的一个模拟输入，
在己侧检测上升沿，即可拿到精确的「帧 ↔ 主机时钟」映射 + 漂移校正，
正好复用现有 `PulseDetector` + `align_shared_pulses` 基础设施。

### 2. `SetSDK` —— 重开 SDK 数据广播（最强纯软件方案）

`SetSDK`（Data=1 使能）可让测力台 + 动捕 Marker 由我们进程实时接收、打 `host_monotonic_ns`，
直接并进主机时钟（每帧都有主机时间戳）。代价：CPU/内存负载增加，.cap 仍是后处理权威记录（等于双份采集）。
现有 SDK 适配器仍在注册表：`XingNokovMocapAdapter` / `XingNokovForcePlateAdapter`。

### 3. `TimeCode` 字段

`CaptureStart` / `CaptureStop` 均带 `<TimeCode>`，当前代码硬编码 `00:00:00:00`。
若配合同步盒 SMPTE 同步 + 己侧 SMPTE LTC 读码器，可做时间码级对齐；单靠该软件字段价值有限。

### 4. `FrameRate` 查询

返回当前文件真实帧率（float），可用于消除「帧号 ÷ 假设帧率」的换算误差。

### 5. `PacketID`

`CaptureStart`/`CaptureStop` 带 `PacketID`（当前写死 0）。改为递增 + 配对请求/响应，
可测往返延迟，回推真实第 0 帧时刻，改善起始偏移精度。

## 四、可选方案（按性价比）

| 优先级 | 方案 | 类型 | 效果 |
|---|---|---|---|
| ★★★ | 同步盒 TTL Out → 接我们一个模拟输入（`SetSyncDevice`） | 硬件（需同步盒） | 每帧一个脉冲，帧↔主机精确对齐 + 漂移校正，**治本** |
| ★★☆ | 重开 SDK（`SetSDK=1`）让测力台+动捕每帧带主机时间戳 | 纯软件 | 同步最强，但要改代码 + 双份采集 |
| ★☆☆ | `PacketID` 往返延迟 + `FrameRate` 查询 + `TimeCode` 探索 | 纯软件 | 只改善起始锚点精度，无漂移校正 |

**建议组合**：先做纯软件小改进（`PacketID` 递增 + 记录发送时刻 + `FrameRate` 查询，几乎零成本）；
确认是否有 Nokov 同步盒和空闲模拟输入，若有则上 `SetSyncDevice` TTL Out 方案（最终解）。
